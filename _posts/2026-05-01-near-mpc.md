**tl;dr:**
_The good:_ Audit went well. Lúcás Meier's Cait-Sith threshold ECDSA protocol seems like a reasonable, conservative choice. All MPC nodes now run in TEEs.
_The pretty good:_ Near's MPC currently works in an 11 out of 16 setting (as of October 23rd, 2026).
_The bad:_ No proactive refresh.

## Thoughts

 - MPC's configuration is transparent, on-chain $\Rightarrow$ can monitor for suspicious membership changes
 - _"uses the Cait-Sith protocol in a secure manner"_[^DIM25]
 - _"we did not identify any issues related to Beaver triple or nonce reuse that could compromise the security of a shared key"_[^DIM25]
 - NEAR only used Cait-Sith on mainnet (as of May 1st, 2026)

    + FROST threshold signatures were added (as of October 23rd, 2026)

### Somewhat concerning

 - Claude Code identified four unaddressed items from the Trails of Bits audit; they are not high-severity though:
   + #4 Ciphertext swapping (DB AAD missing) -- Informational, Cryptography
   + #5 Hash function used as KDF (derive_tweak) -- Informational, Cryptography
   + #6 P2P identity misbinding (duplicate p2p public keys) -- Medium, Data Validation
   + #10 AES-GCM nonce reuse (96-bit random, no rotation) -- Medium, Cryptography
 - NEAR modified the Cait-Sith scheme[^DIM25]
   + multiplicative rerandomization of pre-signatures

### Concerning

 - No robustness and no identifiable abort (AFACCT)
   + a malicious participant who deviates can make signing fail (abort the protocol) and do so without being identifiable by honest parties $\Rightarrow$ 1 participant can DoS
 - NEAR had a lot of GitHub CI security issues in the Trail of Bits report (#12, #13, #14[^DIM25])
   + #14 could've allowed an attacker to release a completely malicious binary (was rated "difficult" though)

### Deeply concerning

 - **No proactive refresh**, even though re-sharing (for nodes leaving and joining) is implemented and would be trivial to call periodically
    + Without proactive refresh, an attacker can slowly take its time and compromise all 11 keys
    + The last re-sharing (and thus refresh) was on October 22nd, 2026
        * Re-sharings have been roughly monthly since May 2026, but only because membership changed; nothing guarantees this cadence
        * $\Rightarrow$ as of May 1st, 2026, there had been no re-sharing for 2 months, so any progress an attacker made during that time was still good progress
    + **Why not?** Because [proactive refresh must invalidate the ECDSA pre-signatures](#proactive-refresh), which lowers performance.
 - The Cait-Sith threshold ECDSA library was not part of the audit; only its use by NEAR's MPC node implementation was audited[^DIM25]
   + This library may not have been production-ready.

## Cryptography

### Why no proactive refresh?
{: #proactive-refresh}

Adopting [this notation](https://alinush.github.io/ecdsa#algorithms), recall that a pre-signature for $R = k \cdot G$ is a secret sharing:

$$([k^{-1}]_i, [k^{-1}\cdot \sk]_i)_{i\in[n]},$$

where:
 - $[k^{-1}]_i$ is player $i$'s ($t$-out-of-$n$) share of the inverted nonce $k^{-1}$
 - $[k^{-1}\cdot \sk]_i$ is player $i$'s share of $k^{-1}\cdot \sk$

Pre-signatures on their own are indifferent to the secret-sharing of $\sk$ changing: they remain valid.
So, we can proactively refresh $\sk$ without invalidating the pre-signatures.
So then why isn't there any proactive refresh on NEAR's MPC?
My best guess?
It's because $\sk$ refresh is only meaningful if presignatures are refreshed too.

In other words, if $\ge t$ shares of a pre-signature leak, then that would reveal $k^{-1}$ and $k^{-1}\cdot \sk$, and thus reveal $\sk$.
So an attacker will simply shift from compromising $\sk$ shares over a long period of time, to compromising pre-signature shares.
Why aren't presignatures refreshed?
My best guess is that, this would require a lot of work[^proactive-refresh].

Even if pre-signatures were proactively refreshed, Cait-Sith relies on Beaver triples[^Beav92] to quickly compute the pre-signatures.
For example, to get shares $[k^{-1}\cdot \sk]\_i$ from shares $[k^{-1}]\_i$[^more] and $[\sk]\_i$, first, assume you have a Beaver triple sharing $([a]\_i,[b]\_i,[ab]\_i)$ where $a,b$ are random.
Then, compute shares of _masked values_: $[\alpha]\_i\bydef [k^{-1}]\_i + [a]\_i$, and $[\beta]\_i\bydef [\sk]\_i + [b]\_i$.
Then, reconstruct the masked values: $\alpha = k^{-1} + a$ and $\beta = \sk + b$.
These reveal nothing since $a, b$ are random.
Then, note that $k^{-1}\cdot\sk = (\alpha - a)\cdot\sk = \alpha\cdot\sk - a \cdot \sk = \alpha\cdot\sk - a\cdot(\beta - b) = \alpha\cdot\sk - \beta\cdot a + ab$, which is linear in the shared $\sk$, $a$ and $ab$.
So, each player can locally compute $[k^{-1}\cdot\sk]\_i = \alpha\cdot[\sk]\_i - \beta\cdot[a]\_i + [ab]\_i$.

From the above, we can tell that a leak of $a$ (or $b$), once the triple is consumed and $\alpha$ (or $\beta$) is revealed, would leak $k^{-1}$ (or $\sk$).
Recall that, given $k^{-1}$ and a signature $(r,s)$ and the signed message $m$, one can recover $\sk$.
Therefore, Beaver triples should also be proactively refreshed to minimize the likelihood that a long-term attacker can pull off such a stunt.
Again, as with pre-signature refresh[^proactive-refresh], such Beaver triple refresh is expensive too: 1.5x more expensive, in fact, since Beaver triples have 3 secret-shared values, while pre-signatures have 2.

{: .note}
As of September 2026, NEAR added an [online presign-and-sign](https://github.com/Near-One/mpc/blob/2ac7c2a4347896b43ad5fd74e29c3743e479e845/crates/threshold-signatures/src/ecdsa/ot_based_ecdsa/README.md?plain=1#L35) path, which computes the pre-signature only after the signing request arrives and consumes it immediately, so no pre-signatures are stored.
This shrinks the problem a little, since there are no stored pre-signatures left to refresh.
But it does not solve it: the Beaver triples are still precomputed and stored, so they would still need to be refreshed.

### Why presignature rerandomization exists

{: .info}
**tl;dr:** Rerandomization prevents an $O(q^{1/3})$-time forgery attack on ECDSA with presignatures and additive key derivation, due to Groth and Shoup[^GS21e].
It does **not** protect against presignature reuse.

NEAR's MPC supports **additive key derivation**: an app's secret key is $\sk + e$, where the **tweak** $e = H(\mathsf{app\\_id}, \mathsf{path})$ is public.
Here, $\mathsf{app\\_id}$ identifies the app requesting the signature[^app-id] and $\mathsf{path}$ is an arbitrary **derivation path** chosen by the app (e.g., `alice@gmail.com/bitcoin`), which lets one app control many keys.
A presignature for the master $\sk$ is locally adapted to $\sk + e$ via:

$$[k^{-1}\cdot(\sk + e)]_i = [k^{-1}\cdot \sk]_i + e\cdot [k^{-1}]_i$$

The problem is that, with presignatures, $R$ (and thus $r$) is known **before** the message $m$ and the tweak $e$ are chosen (e.g., any corrupted MPC node knows it).
Groth and Shoup[^GS21e] show this enables a forgery: find $(m,e)\ne(m^\*,e^\*)$ such that $H(m) + r\cdot e = H(m^\*) + r\cdot e^\*$, and ask for a signature on $m$ under tweak $e$.
Since $s = k^{-1}(H(m) + r\cdot e + r\cdot\sk) = k^{-1}(H(m^\*) + r\cdot e^\* + r\cdot\sk)$, it is also a valid signature on $m^\*$ under tweak $e^\*$.
Finding such a pair is a 4-sum problem, which Wagner's algorithm[^Wagn02] solves in $O(q^{1/3})$ time when enough tweaks are available, faster than the best $O(q^{1/2})$ attack on plain ECDSA.

Groth and Shoup's fix is to **rerandomize** the presignature at signing time via $R \gets R + \delta\cdot G$ (i.e., $k\gets k+\delta$), where $\delta$ is public but unpredictable.
Since $r$ is now unknown when $(m,e)$ is chosen, the attack no longer works.

NEAR instead rerandomizes **multiplicatively**: the new nonce is $k' \bydef \delta\cdot k$, so $R' = \delta\cdot R$ and $k'^{-1} = \delta^{-1}\cdot k^{-1}$.
Combined with the key derivation above, each player [computes](https://github.com/Near-One/mpc/blob/2ac7c2a4347896b43ad5fd74e29c3743e479e845/crates/threshold-signatures/src/ecdsa/ot_based_ecdsa/presign.rs#L108-L138) its shares of the new presignature for $\sk + e$, starting from its old shares $[k^{-1}]_i$ and $[k^{-1}\cdot\sk]_i$.
First, the inverted nonce share is simply scaled by $\delta^{-1}$:

$$\delta^{-1}\cdot [k^{-1}]_i = [\delta^{-1}\cdot k^{-1}]_i = \emph{[k'^{-1}]_i}$$

Second, the other share is shifted by $e$ and then scaled by $\delta^{-1}$:

\begin{align}
\delta^{-1}\cdot\left([k^{-1}\cdot\sk]_i + e\cdot[k^{-1}]_i\right)
    &= \delta^{-1}\cdot[k^{-1}\cdot\sk + e\cdot k^{-1}]_i\\\\\
    &= \delta^{-1}\cdot[k^{-1}\cdot(\sk + e)]_i\\\\\
    &= [\delta^{-1}\cdot k^{-1}\cdot(\sk + e)]_i\\\\\
    &= \emph{[k'^{-1}\cdot(\sk + e)]_i}
\end{align}

Here, $\delta$ is [derived](https://github.com/Near-One/mpc/blob/2ac7c2a4347896b43ad5fd74e29c3743e479e845/crates/threshold-signatures/src/ecdsa/rerandomization.rs#L65) via HKDF from $(\pk, e, H(m), R, \mathsf{participants})$, keyed by the NEAR block's [random value](https://github.com/Near-One/mpc/blob/2ac7c2a4347896b43ad5fd74e29c3743e479e845/crates/chain-gateway/src/event_subscriber/streamer/block_processor.rs#L79), which the requester cannot predict.
Recall that $\pk = \sk\cdot G$ is the master public key; $\mathsf{participants}$ is the set of MPC nodes taking part in this signing session.

{: .note}
As mentioned earlier, NEAR added an [online presign-and-sign](https://github.com/Near-One/mpc/blob/2ac7c2a4347896b43ad5fd74e29c3743e479e845/crates/threshold-signatures/src/ecdsa/ot_based_ecdsa/README.md?plain=1#L35) path, which computes the pre-signature only after the signing request arrives and consumes it immediately, so no pre-signatures are stored.
This path [skips](https://github.com/Near-One/mpc/blob/2ac7c2a4347896b43ad5fd74e29c3743e479e845/crates/threshold-signatures/src/ecdsa/ot_based_ecdsa/presign.rs#L75-L85) rerandomization (i.e., $\delta = 1$), since $R$ is only computed after $(m, e)$ is chosen, so the attack above does not apply.

Two caveats:
 - Groth and Shoup only prove security for additive rerandomization with a random $\delta$; they leave hash-derived $\delta$ unanalyzed, and never consider the multiplicative variant.
 - ToB's audit[^DIM25] notes NEAR did its own analysis of the multiplicative variant, which ToB reviewed only at a high level, recommending further peer review.

[^proactive-refresh]: Specifically, for each presignature, each player refreshes it by dealing two random sharings of 0 to everyone. Then, each player adds the two zero-shares it receives from all players to its two presignature shares.
[^more]: In fact, computing $([k^{-1}]_i, k\cdot G)$ itself also relies on a $(u, d, ud)$ Beaver triple, plus the public points $u\cdot G$, $d\cdot G$ and $ud\cdot G$. Cait-Sith simply sets $k^{-1} \bydef u$, so the players already hold shares of $k^{-1}$. The problem is that $R\bydef k\cdot G$, but only $k^{-1}\cdot G$ is public, and we can't invert inside the exponent. Instead, the players open the product $ud = k^{-1}d$ in the clear, which is safe because the random $d$ masks $k^{-1}$. Everyone then computes $R = (k^{-1}d)^{-1}\cdot(d\cdot G) = k\cdot d^{-1}\cdot d\cdot G = k\cdot G$.
